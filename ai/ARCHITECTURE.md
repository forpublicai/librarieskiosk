# Kiosk Architecture

This document records the durable, app-level architecture of Libraries Kiosk. [`AGENTS.md`](../AGENTS.md) tells agents how to *work* in the repo; this file describes how the kiosk itself is *structured*.

When adding architectural notes, follow the LEARNINGS scope ladder (see [LEARNINGS.md](../LEARNINGS.md)): if it is **app-specific architecture / policy**, it belongs here; if it is symbol-local, put it in a docblock; if it is repo-wide engineering wisdom, put it in `LEARNINGS.md`.

---

## 1. High-level shape

```
┌──────────────────────────────────────────────────────────────┐
│  Kiosk browser (locked-down Chrome on library hardware)      │
│  Start URL: https://host/l/<slug>?access=<KIOSK_ACCESS_TOKEN>│
└─────────────────────────────┬────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│  Next.js App Router (Vercel)                                 │
│                                                              │
│  middleware.ts → kiosk_access cookie gate (HTML 403)         │
│  /l/[slug]      → kiosk_library cookie + redirect to /       │
│  /api/auth/*    → JWT issue/verify, ActiveSession            │
│  /api/{mode}    → credit deduct, usage log, NanoGPT call,    │
│                   optional R2 persistence                    │
│  /api/guide     → tier-aware live answer (no credit deduct)  │
│  /admin /api/admin/*                                         │
│  /admin/superadmin /api/admin/superadmin/*                   │
└──────┬────────────────────────┬──────────────────────────────┘
       │                        │
       ▼                        ▼
┌─────────────────┐   ┌─────────────────────────────────────┐
│ Postgres (Neon) │   │ NanoGPT (chat/code/image/video/music)│
│ User, Library,  │   │ Per-library API key                  │
│ ActiveSession,  │   └─────────────────────────────────────┘
│ Conversation,   │            │
│ UsageLog,       │            │ generated bytes
│ MediaSession,   │            ▼
│ CreditRequest   │   ┌─────────────────────────────────────┐
└─────────────────┘   │ Cloudflare R2                        │
                      │ media/{mode}/{userId}/{yyyy}/{mm}/   │
                      │  {uuid}.{ext}                        │
                      │ AVIF for images, MP4 for video,      │
                      │ MP3 for audio                        │
                      └─────────────────────────────────────┘
```

Single Next.js deployment serves all libraries. Per-library identity is established by the kiosk's start URL (`/l/<slug>`), which sets a long-lived (8h) `kiosk_library` cookie. From that point on every guest login, generation call, and credit deduction is library-scoped through the cookie → `User.library` → slug → env-var chain.

Weekly credit renewal is the one scheduled app maintenance path: Vercel cron calls `/api/cron/renew-credits` at the Monday 12:00am America/Chicago boundary (via UTC schedules that cover Central Standard and Daylight Time). The endpoint is guarded by `CRON_SECRET`, and normal login/read/generation/admin paths still run the same reset helpers as a fallback if cron is delayed or missed.

## 2. Identity and access control

### 2.1 Roles

| Role | Created by | Can sign in | Status gate | Capacity gate | Sessions |
|------|------------|-------------|-------------|---------------|----------|
| `SUPER_ADMIN` | seed only | yes | bypass | bypass | no row |
| `ADMIN`       | seed / super-admin tooling | yes | bypass | bypass | no row |
| `PATRON`      | self-signup | yes | enforced (`PENDING` blocks generation) | enforced | `ActiveSession` row |
| `GUEST`       | seed (one per library + legacy `guest`) | "Continue as Guest" only | always APPROVED | bypass | no row, ephemeral |

### 2.2 Two access gates — they are independent

1. **Kiosk-device gate** — `middleware.ts` checks the `kiosk_access` cookie or `?access=<KIOSK_ACCESS_TOKEN>`. Anyone outside the kiosk gets a static 403 HTML page. This is per-device, not per-user. If `KIOSK_ACCESS_TOKEN` is unset, dev mode is enabled and everyone is allowed in.
2. **User-account gate** — JWT bearer token in `Authorization: Bearer ...`, verified by `lib/auth.ts`. PATRONs additionally require a live `ActiveSession` row whose `lastActivity` is within `SESSION_IDLE_MS` (10 minutes).

Both gates must pass on every API call. Guests skip the second gate's idle check.

### 2.3 Patron session lifecycle

```
login           → ActiveSession row created with new jti
                  (older idle rows for the library are GC'd first;
                   if at-cap → 409 LIBRARY_AT_CAPACITY)
api/* call      → requireActiveSession touches lastActivity = now()
heartbeat (1m)  → only sent when client has seen real activity
                  (mousedown/move/keydown/touchstart/scroll)
                  → updates lastActivity
inactivity 10m  → server: requireActiveSession deletes row, returns 401
                  client: AuthProvider inactivity timer fires logout()
explicit logout → /api/auth/logout deletes the row
```

Idle rows are also lazy-purged at login time: any `ActiveSession` for a library with `lastActivity < now - 10m` is deleted before the cap check. This keeps the cap from getting jammed by crashed kiosks without needing a cron.

### 2.4 Guest sessions

- Guests share one DB row per library. Concurrent kiosk users at one library all hit the same `guest_<slug>` row.
- Credits renew with the same fixed Monday 12:00am America/Chicago schedule as every other user.
- No conversations / usage logs / media are persisted. Generation routes branch early on `role === 'GUEST'` and return provider URLs with `ephemeral: true`.
- Client-side state (chat history within a session) is kept in `sessionStorage` via `lib/guestSession.ts`, namespaced with `kiosk_guest_*`. Cleared on logout.

## 3. Per-library multi-tenancy

The whole concept of a "library" is layered on top of a *single string* — `User.library` and `Library.name`. There is no foreign key. This is intentional (it lets `User.library = "Guest"` for the legacy guest), but it is also the single largest footgun in the codebase.

The five isolation axes:

| Axis | Source of truth | Enforcement point |
|------|----------------|------------------|
| Patron membership | `User.library` | signup whitelist + every generation route reads it from the JWT |
| Credit pool | `Library.poolRemaining` | `/api/admin/credits` (admin sends from pool) |
| Concurrent sessions | `Library.maxConcurrentSessions` | login + signup capacity check |
| NanoGPT billing | `NANOGPT_API_KEY_<SLUG>` env var | `getNanogptKey(library)` at call time |
| Guest pool | `User.library` on `guest_<slug>` row | `/api/auth/guest` chooses by `kiosk_library` cookie |

`docs/adding-a-library.md` walks through the 7-step checklist for plumbing a new library through all five axes. Skip a step and the failure is silent (e.g., per-library NanoGPT usage shows up under the global key; guest credits drain from the legacy pool).

### 3.1 Slug rule (must match in five places)

```
"Pottsboro, TX" --uppercase, [^A-Z0-9]+ → "_", trim "_"--> "POTTSBORO_TX"
                                          .toLowerCase()  → "pottsboro_tx"
```

Used by:
1. `NANOGPT_API_KEY_<SLUG>` env var lookup (`lib/nanogpt.ts:getNanogptKey`).
2. `/l/<slug>` URL path (`app/l/[slug]/route.ts`).
3. `kiosk_library` cookie value (lowercase form).
4. `guest_<slug>` username (`guestUsernameForLibrary`).
5. Admin tooling that derives env var names from a library row.

Always import the helpers from `lib/library.ts` — `libraryNameToSlug`, `libraryNameToUrlSlug`, `normalizeSlug`, `guestUsernameForLibrary`. Never re-implement the regex.

## 4. Data model

```
User (1) ─┬─ (N) UsageLog
          ├─ (N) Conversation       (chat & code; messages: Json)
          ├─ (N) MediaSession       (image, music, video; R2-backed)
          ├─ (N) CreditRequest      (patron → admin asks for credits)
          ├─ (N) ActiveSession      (patron only; jti unique)
          └─ (N) GuideExchange      (guide quota; jti primary key)

Library                            (no FK from User; matched by name string)
```

Notable fields and invariants:

- **User.role**: `SUPER_ADMIN | ADMIN | PATRON | GUEST`. **User.status**: `PENDING | APPROVED | BANNED`. Generation requires APPROVED; super/admin/guest are seeded APPROVED.
- **User.credits** is the source of truth for available credits. `deductCredits` is atomic and reset-aware: if a user missed the current fixed weekly boundary, it resets and deducts in one DB write. Admins on the dashboard see *the library's pool* (not their own credits) — substituted in the login response.
- **User.creditsResetAt** records the most recent fixed Monday 12:00am America/Chicago renewal boundary. **Library.poolResetAt** does the same for library pools. These are not per-user moving windows.
- **User.lastLoginAt** records the last successful password, signup auto-login, or guest login. Legacy users with `loginCount > 0` and no timestamp display as `Unknown`; users with no logins display as `Never`.
- **MediaSession.storageStatus**: `PENDING → UPLOADING → UPLOADED | FAILED`. The transition is atomic via `updateMany` to claim the upload, so concurrent video pollers can't double-upload. `UPLOADING → UPLOADED` happens after the bytes land in R2.
- **MediaSession.checksum**: SHA-256 of the encoded bytes. Used for per-user dedup (same user re-prompts → reuse the existing object key, skip upload, write a new row pointing at the old key).
- **MediaSession.resultUrl** is legacy; new rows store nothing here. R2 lookups go via `objectKey + getMediaReadUrl`.
- **Conversation.messages** is `Json` containing `[{role, content}, ...]`. Stored verbatim; chat code never replays them as a structured array on the server.
- **ActiveSession.jti** is unique and matches the `jti` claim in the patron's JWT. Heartbeat / requireActiveSession look up by `jti`.
- **GuideExchange.jti** is the durable per-auth-session counter for live Learning Guide questions. It covers patrons and guests, increments through an atomic guarded `updateMany`, and is lazily pruned after 24h.

## 5. Request flows

### 5.1 First kiosk visit

1. Browser opens `https://host/l/pottsboro_tx?access=TOKEN`.
2. `middleware.ts` matches `?access`, sets `kiosk_access` cookie (8h), redirects to `/l/pottsboro_tx`.
3. `/l/[slug]/route.ts` validates the slug against the `Library` table, sets `kiosk_library=pottsboro_tx` cookie (8h), redirects to `/`.
4. Landing page renders `<LoginPage>`; user clicks "Continue as Guest".
5. `POST /api/auth/guest` reads the cookie, finds `guest_pottsboro_tx`, signs an 8h JWT.
6. `AuthProvider` stores the token in `localStorage['kiosk_token']`, navigates to `/dashboard`.

### 5.2 Patron login

1. `POST /api/auth/login` validates credentials, checks status (BANNED → 403).
2. For PATRONs only: GC stale `ActiveSession` rows for the library, count remaining, reject with 409 LIBRARY_AT_CAPACITY if `>= maxConcurrentSessions`.
3. Otherwise create a fresh `ActiveSession` and sign a JWT with the new `jti`.
4. Login response substitutes `Library.poolRemaining` for `User.credits` if the user is an ADMIN (so the admin UI sees pool credits, not personal credits).

### 5.3 Generation (image example)

1. Client → `POST /api/image` with `Authorization: Bearer <jwt>` and `{prompt}`.
2. `requireActiveSession` → `requireApproved`.
3. Fork on `role === 'GUEST'`:
   - GUEST: deduct credits, log usage, call NanoGPT, return `{url|b64_json, ephemeral: true}`. Done.
   - else: same plus persistence.
4. Persistence path (`isR2Enabled() === true`):
   1. Fetch the bytes (provider URL via SSRF-safe fetch, or decode `b64_json`).
   2. `encodeImageWithThumbnail` → AVIF full + thumbnail.
   3. Compute SHA-256. If `MediaSession` already exists for this `userId` with `storageStatus=UPLOADED` and matching checksum → write a new row reusing the existing `objectKey`/`thumbnailKey`, skip upload, return `deduplicated: true`.
   4. Otherwise upload full + thumbnail to R2 in parallel, then write the `MediaSession` row (rolling back R2 objects if the DB insert fails).
   5. Generate signed read URL via `getMediaReadUrl` (cached or freshly signed).
5. Persistence path (`isR2Enabled() === false`): return raw provider data; the client posts to `/api/media-sessions` to persist metadata only (legacy path).

### 5.4 Video (asynchronous)

1. `POST /api/video` submits to NanoGPT, gets `runId`. If R2 is enabled, create a `MediaSession` row with `storageStatus=PENDING` and `providerRunId=runId`.
2. Client polls `GET /api/video/status?requestId=...`.
3. When NanoGPT reports COMPLETED, the status route calls `finalizeVideoUpload`, which does an atomic `updateMany PENDING → UPLOADING` claim. The winner uploads; losers (concurrent pollers) observe the final state.
4. On success → row becomes UPLOADED with `objectKey/mimeType/byteSize/checksum`; signed URL returned. On failure → FAILED.

## 6. Storage layer

- **`lib/storage.ts`**: S3 SDK wrapper for R2. Lazy client. `forcePathStyle: true` (R2 requires it). Object keys `media/{mode}/{userId}/{yyyy}/{mm}/{uuid}.{ext}` — `userId` is sanitized; UUID guarantees uniqueness within the same month-bucket. `generateSignedGetUrl(key, ttl?, { downloadFilename? })`: when `downloadFilename` is set, the signed URL bakes `ResponseContentDisposition: attachment; filename="..."` into the *signature* — that header has to be part of the signed query, not appended client-side.
- **SSRF guard** for `uploadFromUrl` / `fetchBytesFromUrl`: HTTPS only, DNS lookup before fetch with private-IP rejection (IPv4 + IPv6 incl. `::ffff:` v4-mapped), `redirect: 'manual'` with max 1 hop, content-length pre-check, content-type allow list, no forwarded auth/cookies. Download proxy callers also pass `DOWNLOAD_PROXY_ALLOWED_HOSTS`; the original URL and every redirect target must be on the allowlist.
- **`lib/imagePipeline.ts`**: sharp pipeline → AVIF full (q60) + thumbnail (max 320px, q45). Failure falls back to original PNG.
- **`lib/mediaPersistence.ts`**: orchestrator between routes and storage. Each `persistXxxResult` writes a `MediaSession` even on failure (UI still gets *something*). Best-effort cleanup of half-uploaded objects.
- **`lib/mediaUrlCache.ts`**: read-URL resolution. Public base URL → cacheable URL (preferred when set); else memoized signed URL with 5-min refresh margin. Per-pod memo, no shared cache needed (objects are immutable).
- **Forced-attachment download path**: `GET /api/media-sessions/[id]/url?download=true` calls `generateSignedGetUrl` with a `downloadFilename` and bypasses the URL cache (the cached URL doesn't have `Content-Disposition: attachment` baked in). Generation pages call this when the user clicks Download; falling back to a blob fetch only for legacy/guest cases that don't have a sessionId. Without the forced disposition, R2 cross-origin presigned URLs render in the browser instead of downloading because the `<a download>` hint is ignored cross-origin. Patron and guest proxy fallbacks both require `mode` so the MIME allowlist maps `image → image/*`, `music → audio/*`, and `video → video/*`.
- **Video failure fallback**: `MediaSession.sourceProviderUrl` is the provider's original URL, written by `finalizeVideoUpload` on both the atomic claim and the failure handler. If R2 upload fails, `/api/media-sessions` returns it as `legacyUrl` so the patron's history item still plays for as long as the provider URL stays alive.

## 7. Frontend

- App Router with one root `layout.tsx` that wraps everything in `AuthProvider`. The inline theme-flash-prevention `<script>` is in `<head>`; the visible toggle is no longer in the root layout.
- `AuthProvider`:
  - Keeps `user` + `token` in React state, mirrored to `localStorage['kiosk_token']`.
  - On mount: if a token exists, calls `/api/auth/me`; on 401, logs out.
  - 10-minute inactivity timer (mouse/keyboard/touch/scroll); fires `logout()`.
  - 1-minute heartbeat (PATRONs only) — only pings if `hadActivityRef` was set since the last tick. Idle kiosks let their server session lapse naturally.
  - Logout flow: best-effort `/api/auth/cleanup` (guest only) + `/api/auth/logout` + clears local state + `clearAllGuestState()`. Guest logout also clears the current token-scoped guide-tier key so shared guest accounts don't leak guide state.
- `Header`: shows credit badge, optional `actions` slot for per-page chrome (used by the Learning Guide button), `<ThemeToggle>`, sign-out. The `actions` prop is the canonical extension point — never reach for a parallel `<Header2>`.
- `ThemeToggle`: light/dark toggle persisted in `localStorage['theme']`. SSR-safe initial class set by an inline `<script>` in `layout.tsx` to avoid theme flash. Renders in the visible chrome for each page family: `Header` on generation pages, info-page topbars, dashboard header, and a small floating wrapper only on pre-auth screens with no chrome.
- `GuidePanel`: per-tool side panel with tier-gated static content (`config/guide/<tool>.json`) plus a free-form input that fuzzy-matches FAQs, falls through to `/api/guide` when no static match is found. Mounted by every generation page; visible only when the per-page `guideOpen` state flips it open. See §11.
- `CoachmarkTour`: per-tool first-visit page tour that anchors to `data-tour="..."` attributes. Per-user-per-tool dismissal state in `localStorage['cm_<username>_<tool>']`. Restartable from `GuidePanel` via the `cm-restart` window event.
- Pages: each mode (`/chat`, `/image`, `/video`, `/music`, `/code`) is a single `'use client'` page that fetches once, manages its own state, and posts to its API route. No global state library. Each page tags its key regions with `data-tour="<id>"` attributes for the tour, and passes a `<button data-tour="guide-btn">` into `Header.actions`.
- `useGenerationProgress`: shared progress UI hook for long-running generations (mostly video).

## 8. Configuration

- **`config/models.json`**: model IDs and labels per mode. **Always** read from this — no model IDs in route handlers.
- **`.env.example`**: canonical list of env vars. Update it whenever a new env var is required, even if the value is left empty.
- **`CRON_SECRET`**: required in deployed environments so Vercel cron can call `/api/cron/renew-credits` with `Authorization: Bearer <secret>`.
- **`vercel.json`**: contains the credit-renewal cron schedules. Vercel cron is UTC-only, so the app schedules both `05:00 UTC` and `06:00 UTC` on Mondays; the reset predicate prevents early/duplicate renewal and covers DST.
- **`prisma.config.ts`** + **Prisma 7** with `@prisma/adapter-pg` (the new `prisma-client` generator outputs to `src/generated/prisma`).
- **`prisma/seed.ts`**: idempotent. Re-running won't reset balances or roles. The per-library guest loop iterates over the array of library upserts — adding a new library upsert without adding it to the loop array breaks isolation.

## 9. Observability and ops

- Console logs are the current observability surface (server logs visible in Vercel). Look for `[guest login] no kiosk_library cookie ...` to spot kiosks that haven't been re-provisioned with a library URL.
- Credit renewal logs/errors come from `/api/cron/renew-credits`; its JSON response includes `usersRenewed`, `libraryPoolsRenewed`, and `checkedAt`.
- `npm run test` currently covers the Central-time weekly renewal window, including DST edge cases.
- `npm run smoke-test` exercises the API surface end-to-end against a deployed environment.
- `npm run probe:nanogpt` is for diagnosing key/model/availability issues quickly.
- `scripts/backfill-media-to-r2.ts` re-uploads legacy media into R2 for environments migrating from the pre-R2 era.
- `prisma/scripts/move-to-public-ai.ts` is the canonical pattern for one-off ops scripts (env-loaded, separate Prisma client, exit codes).

## 10. Learning Guide and onboarding

The kiosk's audience often includes patrons who have never used a generative-AI tool. Two complementary surfaces lower that floor without bloating the chrome of the generation pages.

### 10.1 `GuidePanel`

A side panel mounted on every generation page, opened by a header button. State machine:

```
tier-select → entry-point → ┬→ what-is-it
                            ├→ use-cases → getting-started ────┐
                            │                  ↘                │
                            │                   open-question ──┤
                            └→ faq-categories → faq-list →     ──→ faq-answer
                                                                    (free-form input)
```

The "tier" — the user's stated experience level — is the dominant axis. It is stored in namespaced localStorage keys: `guide_tier_user_<id>` for patrons/admins and `guide_tier_guest_<token-fragment>` for guests. The legacy unscoped `guide_tier` key is removed on guide mount/logout. The tier is read once on first open and mirrored into the panel-header chip ("New to tech ✎" etc.) so the user can change it at any time. The chip pulses once after first selection to draw attention to its existence.

**Static content** lives in `config/guide/<tool>.json` (chat, code, image, video, music). The schema:

```ts
{
  whatIsIt:   { tier1, tier2, tier3 },          // free text, "\n\n" → bubble break
  useCases:   [{ id, label, gettingStarted: { intro, examplePrompt, tips[], cautions[] } | null }],
  faqs:       { concept, practical, criticalUse }      // each is [{ q, a }]
}
```

The last use-case in every file (`gettingStarted: null`) is the open-input fallback ("I have something else in mind"). Authored copy is sourced verbatim from PDFs; do not paraphrase.

**Free-form input** is allowed on every screen except `tier-select`. On submit:

1. Fuzzy-match against `useCases` (score ≥ 0.25). On hit → render that use-case's getting-started bundle.
2. Else fuzzy-match against the union of all FAQs (score ≥ 0.35). On hit → render the answer.
3. Else → call `/api/guide` with the question, tool, and tier. Render bubble-by-bubble.

The fuzzy matcher (a) normalizes intent-framing wrappers (`I don't know what X is` → `X`), (b) tokenizes against a hand-tuned 60-word stop list, (c) **rejects orphan tokens** — if a query token doesn't appear anywhere in the FAQ corpus the question is by construction beyond the static content and is routed to the live model, and (d) does a **two-pass score**: question-text first (disambiguates between FAQs whose answers share vocabulary), combined-text fallback. These specific behaviors exist because they were debugged into the matcher to fix false positives ("I don't know what a JPEG is" matching the file-format FAQ; "Is PNG the same as JPEG?" matching the JPEG FAQ via incidental shared words).

**Bubble cadence**: bot bubbles are queued through `setTimeout(500ms)` chains with a typing-dots indicator between them. Both static and live answers split on `\n\n` so multi-paragraph content reads as several short messages.

### 10.2 `/api/guide`

`POST /api/guide` body: `{ question, tool, tier: 1|2|3 }`.

- Auth: `requireActiveSession` + `requireApproved` (same gate as every generation route).
- Generic NanoGPT key via `getGenericNanogptKey()`, intentionally keeping onboarding spend off individual library billing keys.
- Model: `modelConfig.chat.model` (the chat tool's model — small, fast, conversational).
- `tool` is allowlisted to `chat | code | image | video | music` before prompt construction or quota reservation.
- System prompt is composed from `TOOL_DESCRIPTIONS[tool]` + `TIER_LABELS[tier]` + `TIER_GUIDANCE[tier]`. The tier guidance is what actually changes the response complexity — Tier 1 forces plain-English with everyday analogies, Tier 3 allows AI-specific terminology.
- An off-topic guard in the system prompt instructs the model to politely deflect to the matching tool's own guide if the question isn't about the current tool.
- **Stateless.** No conversation history is sent. Each call is one question + one answer. (Multi-turn follow-up is a known gap, deferred.)
- **Not credit-deducted.** The route does not call `deductCredits`. Patron successes still write `UsageLog` rows with `mode: 'guide'` and `creditsUsed: 0` for visibility; guests do not write usage logs.
- **Rate-limited per auth session.** `GuideExchange` is keyed by JWT `jti`; the route reserves a slot before calling NanoGPT with an atomic guarded increment. The 6th question returns the librarian redirect without a model call. Signing out and back in creates a new JWT and therefore a fresh guide quota.

The non-streaming `chatComplete()` helper in `lib/nanogpt.ts` is used here (and only here) — the response is short enough that streaming adds complexity for no gain.

### 10.3 `CoachmarkTour`

Per-tool first-visit page tour. Anchors to elements via `data-tour="<id>"` attributes — a deliberate decoupling so the page markup can be rearranged without touching the tour content.

- Tour content lives inside `CoachmarkTour.tsx` as `TOURS: Record<tool, Step[]>`. Each step has `{ target, title, body, pos }`.
- Storage key `cm_<username>_<tool>` (or `cm_anon_<tool>` for guests). Once dismissed, never reappears for that user-on-that-tool unless explicitly restarted.
- Restart channel: `GuidePanel` removes the storage key and dispatches a `cm-restart` `CustomEvent` on `window`; `CoachmarkTour` listens, resets state, and replays.
- Visual: four-rect backdrop carving a hole around the target, a glowing ring around the hole, and a fixed-position tooltip clamped to the viewport.

## 11. Boundaries: what this app deliberately does *not* do

- **No payments.** Credits are an internal abstraction over weekly grants; there is no purchase flow.
- **No PII.** Username + library + bcrypt password hash + bcrypt security-answer hash. No emails, names, or phone numbers.
- **No social features.** Conversations and media are private to the user; admins do not browse user content.
- **No realtime collaboration.** Each session is single-user.
- **No background workers.** Everything runs in request handlers, with one exception: Vercel cron calls `/api/cron/renew-credits` for fixed weekly credit renewal. Video status polling is still client-driven.
- **No CDN at the app layer.** Cloudflare in front of R2 (when `R2_PUBLIC_BASE_URL` is set) is the only caching layer. App responses are `dynamic = 'force-dynamic'`.
